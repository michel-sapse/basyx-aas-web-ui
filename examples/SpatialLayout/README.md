# Asset positional-data preview

The plugin recognizes the supplied Asset Positional Data semantic ID
urn:apeirora.eu:idcm:cd:assetPositionalData:Submodel.
PositionalData.json is the unmodified user-supplied sample. The environment.json
and aas/SpatialLayoutDemo.aasx files are a **synthetic demo derived from it**,
with a rack-front surface, two server shells and explicit test mounting targets.
This is not a newly claimed IDTA template or a measurement of actual servers.

## Try it with Colima

Run these commands yourself when ready. They build the current source and start
a separate stack; they do not recreate the TimeSeries containers:

~~~bash
cd /Users/I745178/Documents/hackathon/basyx-aas-web-ui/aas-web-ui
pnpm build
cd ../examples/SpatialLayout
docker --context colima compose up -d --build
~~~

Open **http://localhost:14000**, select **RackDemo**, then **PositionalData**,
and switch to its visualization view if the generic element list is shown.
The API is http://localhost:19081. The database has its own named volume.

Select **Server 01 · offset demo**. Its stored Z is **22 Rack Unit**; the green
mounting target is **20 Rack Unit**. Click **Front**, then **Focus selection**.
Edit Z to 20 or choose **Preview target position**. The gray outline retains
the saved placement, and the numeric offset becomes zero. **Cancel** makes no
write. **Save coordinates** persists the selected XYZ collection. Refresh the
page to check Z remains 20. X, Y, Euler angles and PositionsOffset remain intact.
Use the asset selector or click a mesh; use an individual gizmo axis to drag.
Keyboard users can edit the XYZ fields and activate Save or Cancel.

For later source changes, repeat the source build, then:

~~~bash
docker --context colima compose up -d --build --no-deps aas-web-ui
~~~

Uploading the original sample through the AAS Editor is also supported. Without
geometry or a known mounting target, the viewer shows an anchor marker and the
real area polygon; it cannot infer the correct location.

## Coordinate contract and limitations

- The sample declares +Z up, +X forward, Cartesian coordinates and intrinsic
  Euler order YPR. X/Y are metres; Z is Rack Unit, **0.04445 m per stored unit**.
  Z 22 → 20 moves by 0.0889 m (88.9 mm), not 2 cm or 2 m.
- LengthUnitX/Y/Z each declare a Name, MultiplyingFactor and PhysicalUnit
  reference. Supported physical bases are metre (0173-1#05-AAA551#006) and
  degree (0173-1#05-AAA117#005). Other bases are rejected, not guessed.
- Each Positions list entry uses Asset to identify its AAS, and its
  CoordinateSystemReference must resolve to this submodel's CoordinateSystem.
  External frames and nested parent frames need a future reference resolver.
- Displayed anchor = CartesianCoordinates + PositionsOffset.CartesianCoordinates,
  converted independently along each axis. The area polygon uses its referenced
  frame without the asset offset. Plane YZ maps polygon Xvalue to Y and Yvalue to
  Z. There is no inferred geographic origin or camera-based data transformation.
- The viewer uses a right-handed display basis, with declared up/forward mapped
  to camera up/front. Geographic control points and sea-level data are preserved
  but do not establish a complete geographic placement transform.
- Zero Euler angles give the declared facing direction. Nonzero rotations are
  retained and clearly flagged; their exact rotation axes require confirmation
  before orientation rendering/editing. Position editing remains available.
- The demo adds optional PreviewName (Property), PreviewGeometry and
  MountingReference (XYZ collections). Geometry is a centered axis-aligned box
  with spans in each declared axis unit; references are pre-offset coordinates.
  These are documented demo extensions, never generated by the viewer.

## Save contract

Selection uses the stable Asset AAS identifier, not a display name or list index.
Save re-reads the submodel and resolves the current list index by that identity.
It checks the original position, units, shared offset, orientation and reference
context for concurrent changes. Only changed values in a cloned, fresh
CartesianCoordinates collection are replaced; metadata and unchanged lexical
values are retained. The client sends an AAS API PUT to
/submodels/{base64url-id}/submodel-elements/Positions[index].CartesianCoordinates,
then reads the submodel again to confirm the saved values. No request occurs on
typing, dragging, target preview or Cancel. Failed/denied/unconfirmed saves retain
the draft. Editing respects the UI feature flag and backend authorization.

This is best-effort conflict detection; a concurrent write between the fresh read
and PUT cannot be prevented without backend conditional-write support. Refresh
retains drafts and establishes a newly reviewed baseline. Changes to the shared
frame require canceling drafts first. Switching selection retains per-asset edits.
Saving one asset keeps the original comparison baseline of other unsaved assets,
so concurrent changes to those assets are detected when they are later saved.

## Reproduce and verify

From aas-web-ui, regenerate the artifacts after intentional demo changes:

~~~bash
pnpm exec node ../examples/SpatialLayout/generate.ts
pnpm lint:check
pnpm test:run tests/components/Plugins/Submodels/SpatialLayout
pnpm type-check
~~~

The generator validates the complete AAS environment using AAS Core and packages
an AAS 3.1 XML specification using the existing AASX library. Unit tests consume
both the original sample and generated environment. The browser test is opt-in
and uses an already running **current source** demo, with no automatic build:

~~~bash
IT_DISABLE_WEBSERVER=true pnpm exec playwright test --project=integration-spatial
~~~

It previews a temporary correction, verifies no PUT until Save, checks the real
API response, then restores the original Z through Save. It operates only on this
dedicated synthetic demo. Browser/runtime verification requires the stack above.
